# Open questions — answered (Oct 15 2026)

| Question | Answer | Evidence |
|---|---|---|
| Can an approved operator call `voter.reset`? | **Yes.** `Voter.reset` checks `ve.isApprovedOrOwner(msg.sender, id)`. But `onlyNewEpoch` blocks it in the same epoch as the last vote and during the first hour after the Thursday 00:00 UTC flip (`DistributeWindow`). Voted locks are claimable from **01:00 UTC Thursday**. | tigris `Voter.sol:105,180`; fork test `test_fork_votedLock_vaultResetsAndRelocks` (real Voter on testnet) |
| Does `withdraw` pay native BTC or the ERC-20? | It calls `IERC20(token).safeTransfer(msg.sender, value)` on the BTC precompile `0x7b7C…`. On Mezo that precompile **is** the native balance (veBTC's `balanceOf` via the precompile == `eth_getBalance` == 873.614 BTC), so the operator receives native BTC. Payout goes to **msg.sender (the vault)**, not the owner — the vault forwards it. | tigris `ve/Escrow.sol:422-457`; `cast` checks; fork test on real expired lock #9 |
| BorrowerOperationsSignatures format & nonce | Standard EIP-712, domain `("BorrowerOperationsSignatures", "1", 31611, 0xD757…639e)` (read from `eip712Domain()`). Type `OpenTrove(uint256 assetAmount,uint256 debtAmount,address borrower,address recipient,uint256 nonce,uint256 deadline)`; `assetAmount = msg.value` so collateral must be fixed at signing. Nonce = `getNonce(borrower)`, per-borrower counter incremented by every …WithSignature call. ECDSA only (no ERC-1271). Needs SortedTroves hints in practice — zero hints ran out of gas on testnet. | musd `BorrowerOperationsSignatures.sol:96,421,604`; fork test `test_fork_musdMode_opensRealTroveInOwnersName` opened a real trove; sdk test matches viem `hashTypedData` byte-for-byte |
| sMUSD vault address | **Mainnet: `0xb4D498029af77680cD1eF828b967f010d06C51CC`** ("MUSD Savings Rate", symbol sMUSD, impl `0xb33c…9e87`). Not ERC-4626: `deposit(uint256)` mints to msg.sender (no receiver), plain transferable ERC-20, yield via `yieldIndex`/`claimYield`. **No code at that address on testnet** and no testnet deployment found → MUSD_SAVINGS disabled on testnet (constructor `smusd = 0`). (`0x9171…14F8` is Ditto's dMUSD, not sMUSD.) | mezo docs vault-notices.md; bytecode selectors |
| Real lock duration range | `maxLockTime = 30 days` (tigris deploy script; docs' "1–28 days"). End = `floor((now+d)/1 week)*1 week` and must be `> now` and `<= now+30d` → at most **4 Thursdays ahead**; minimum is "crosses the next Thursday 00:00 UTC" (minutes if created just before). Confirmed: a 30-day request on testnet ended 27 days out, 37 days reverted. | fork test `test_fork_lockDurationRange` |

Other findings
- Mezo's deployed MUSD uses post-london opcodes; fork tests run under `FOUNDRY_PROFILE=fork` (cancun). The vault itself still compiles for london.
- Mezo's oracle precompile (`0x7b7c…15`) can't execute in a local fork; tests mock `latestRoundData`/`decimals` with the live shape.
- **The "873.58 BTC at risk" headline is dominated by one test lock (#100, 868 BTC, owner 0x5eaa…8c4d, 350 days unclaimed).** The other 285 expired locks hold ~5.5 BTC. The UI shows the largest lock separately so the pitch stays honest.
